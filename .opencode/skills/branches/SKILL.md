# Ветки

`main` единственная долгая ветка, пул-реквест в неё гоняет проверки (`.github/workflows/ci.yml`). Каждое изменение пишется в своей ветке и приходит в `main` пул-реквестом. Это держит правило репозитория `main`: прямой push отклоняется, слияние только squash и только при зелёной проверке `проверки` на свежей базе. Обхода нет ни у кого, включая администратора.

Ветка рождается из задачи на GitHub и носит имя `<тип>/<номер задачи>-<имя>`: тип тот же, что у коммитов (метка `feature` даёт `feat`, метка `bug` даёт `fix`), имя латиницей в kebab-case, два-четыре слова. У задач имя уже записано внизу строкой «Ветка для разработки:», его берёшь как есть.

Корень репозитория делят несколько сессий сразу. Ветка живёт в своём worktree, корень остаётся на той ветке, где был: переключение в корне уносит чужую незакоммиченную работу и подменяет код под соседней сессией.

Worktree создаётся только в папке `.worktrees` корня, по пути `.worktrees/<ветка>`, где `/` в имени ветки заменён на `-`: ветка `fix/12-scroll-terminal` даёт `.worktrees/fix-12-scroll-terminal`. Копии рядом с репозиторием и в папках других программ не заводятся: их не видно из корня, и через месяц непонятно, чья это работа. Папка стоит в `.gitignore`, иначе `git status` в корне видит копии, а `pnpm lint` в корне проверяет и их код.

## Шаги

1. Задача. Номер называет человек или выбирает сценарий из скилла `autonomous`, иначе `gh issue list --label feature`. Если задачи под изменение нет, предложи завести её с метками типа, `size: S|M|L` и `area: …` и дождись ответа: ветка появляется только после задачи.
2. Ветка и worktree одной командой: `git fetch origin`, затем `gh issue develop <номер> --name <ветка> --base main --checkout --worktree .worktrees/<тип>-<номер>-<имя>`. Внутри `pnpm install`, дальше вся работа только там. Готово, когда `gh issue develop --list <номер>` показывает ветку, `git -C .worktrees/<тип>-<номер>-<имя> branch --show-current` печатает её имя, а `git status` в корне такой же, как до шага.
3. Перед пул-реквестом `pnpm typecheck`, `pnpm lint` и `pnpm test` в worktree: это те же проверки, что в CI.
4. Пул-реквест. `git push -u origin <ветка>`, затем `gh pr create --base main --head <ветка>`, заголовок в формате первой строки коммита, в описании `Closes #<номер>`: слияние само закроет задачу.
5. Слияние. `gh pr checks <ветка> --watch --fail-fast`, при зелёном `gh pr merge <ветка> --squash`: задача приходит в `main` одним коммитом с заголовком пул-реквеста. Отстала от `main`, сначала `gh pr update-branch <ветка>` и снова ждёшь проверку.
6. После слияния, из корня, когда `gh pr view <ветка> --json state --jq .state` печатает `MERGED`: `git worktree remove .worktrees/<тип>-<номер>-<имя>`, `git branch -D <ветка>` и `git push origin --delete <ветка>`. Именно `-D`: после squash ветка не становится предком `main`, и `-d` отказывается её удалять.
