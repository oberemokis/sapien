# sapien

## Код

Устройство, слои и правила против связанности описаны в `docs/architecture.md`, направление зависимостей api и интерфейса проверяет `scripts/check-boundaries.mjs`. Новый модуль сначала получает место в дереве документа, потом код.

Команды: `pnpm typecheck` (tsc и `cargo check`), `pnpm lint` (oxlint, проверка границ, `cargo fmt --check`, secretlint), `pnpm test` (vitest и `cargo test`). Все три гоняет CI, первые два ещё и хук перед коммитом. `pnpm audit:deps` (pnpm audit с уровня high и cargo audit) гоняет отдельный workflow `audit.yml` на пул-реквесте и раз в неделю, исключение записывается с причиной и условием снятия: для npm в `auditConfig` в `pnpm-workspace.yaml`, для Rust в `.cargo/audit.toml`. Api и окно приложения поднимает `pnpm dev`, api и интерфейс в браузере без Rust `pnpm dev:web`, api и Metro для телефона `pnpm dev:mobile`.

Expo ломает API от SDK к SDK, поэтому код телефона сверяется с документацией установленной версии: мажор `expo` из `apps/mobile/package.json` в `https://docs.expo.dev/versions/v<мажор>.0.0/`, оглавление в `https://docs.expo.dev/llms.txt`. Пакет в телефон ставится командой `pnpm expo install <пакет>` из `apps/mobile`: она подбирает версию под SDK.

pnpm ставит только версии старше суток (`minimumReleaseAge`). Если установка дописала `minimumReleaseAgeExclude` в `pnpm-workspace.yaml`, выбранная версия моложе: поставь предыдущую явно и удали запись.

## Коммиты

Формат первой строки здесь Conventional Commits по-русски: `<тип>(<область>): <результат>`. Это перекрывает формат первой строки из скилла `oberemokis-skills:commit`, всё остальное из него действует как есть: тело объясняет причину, автор только пользователь, хуки не обходятся.

- Тип: `feat` новая возможность, `fix` исправление, `refactor` перестройка без смены поведения, `perf` скорость, `test` только тесты, `docs` только документация, `chore` зависимости, CI, конфиги.
- Область: модуль, если правка живёт в одном, иначе сторона (`api`, `desktop`, `tauri` или `mobile`) или `ci`. Правка через весь репозиторий идёт без области: `docs: план функций`.
- Результат: одна фраза по-русски со строчной буквы, без точки, что стало, а не что сделано с файлами.
- Ломающее изменение маршрутов api, формата команд или сохранённых данных: `!` перед двоеточием и в теле строка `BREAKING CHANGE:` с тем, что сломается у потребителя.

Номер задачи в коммит не пишется: связь с задачей держит ветка и пул-реквест.

## Ветки

`main` единственная долгая ветка, пул-реквест в неё гоняет проверки (`.github/workflows/ci.yml`). Каждое изменение пишется в своей ветке и приходит в `main` пул-реквестом. Это держит правило репозитория `main`: прямой push отклоняется, слияние только squash и только при зелёной проверке `проверки` на свежей базе. Обхода нет ни у кого, включая администратора.

Ветка рождается из задачи на GitHub и носит имя `<тип>/<номер задачи>-<имя>`: тип тот же, что у коммитов (метка `feature` даёт `feat`, метка `bug` даёт `fix`), имя латиницей в kebab-case, два-четыре слова. У задач имя уже записано внизу строкой «Ветка для разработки:», его берёшь как есть.

Корень репозитория делят несколько сессий сразу. Ветка живёт в своём worktree рядом с репозиторием, корень остаётся на той ветке, где был: переключение в корне уносит чужую незакоммиченную работу и подменяет код под соседней сессией.

1. Задача. Номер называет человек или выбирает сценарий из «Автономной работы», иначе `gh issue list --label feature`. Если задачи под изменение нет, предложи завести её с метками типа, `size: S|M|L` и `area: …` и дождись ответа: ветка появляется только после задачи.
2. Ветка и worktree одной командой: `git fetch origin`, затем `gh issue develop <номер> --name <ветка> --base main --checkout --worktree ../sapien-<номер>-<имя>`. Внутри `pnpm install`, дальше вся работа только там. Готово, когда `gh issue develop --list <номер>` показывает ветку, `git -C ../sapien-<номер>-<имя> branch --show-current` печатает её имя, а `git status` в корне такой же, как до шага.
3. Перед пул-реквестом `pnpm typecheck`, `pnpm lint` и `pnpm test` в worktree: это те же проверки, что в CI.
4. Пул-реквест. `git push -u origin <ветка>`, затем `gh pr create --base main --head <ветка>`, заголовок в формате первой строки коммита, в описании `Closes #<номер>`: слияние само закроет задачу.
5. Слияние. `gh pr checks <ветка> --watch --fail-fast`, при зелёном `gh pr merge <ветка> --squash`: задача приходит в `main` одним коммитом с заголовком пул-реквеста. Отстала от `main`, сначала `gh pr update-branch <ветка>` и снова ждёшь проверку.
6. После слияния, из корня, когда `gh pr view <ветка> --json state --jq .state` печатает `MERGED`: `git worktree remove ../sapien-<номер>-<имя>`, `git branch -D <ветка>` и `git push origin --delete <ветка>`. Именно `-D`: после squash ветка не становится предком `main`, и `-d` отказывается её удалять.

## Задачи

План живёт в задачах, а не в репозитории: в документах он устаревает молча и расходится с задачами. Поэтому `docs/plan/` стоит в `.gitignore`.

## Автономная работа

Задачи идут одна за другой и доводятся до слияния без вопросов к человеку. Этап это milestone «Этап N. …» на GitHub (`gh api repos/{owner}/{repo}/milestones --jq '.[].title'`), текущий этап открытый с наименьшим N.

1. Вопросы этапа. Собери вопросы из блоков «Что решить до кода» всех задач этапа и из «Открытых вопросов» их эпиков и реши их сам. Ответ с причиной записывается комментарием в задачу, к которой относится вопрос, и повторяется в пул-реквесте этой задачи. Человек правит ответы после слияния своими задачами.
2. Выбор. Следующая задача этапа та, у которой закрыты все задачи из строки «Зависит от».
3. Работа по шагам из «Веток». Задача с отвеченными вопросами считается прошедшей допрос: условия допроса из `oberemokis-skills:core` (больше трёх файлов, несколько слоёв) срабатывают здесь почти на каждой задаче и сами остановку не дают.
4. Проверка вживую. Интерфейс проверяется в `pnpm dev:web` в браузере по пунктам блока «Проверка», скриншоты идут в пул-реквест рядом с образцом. Образец лежит в `docs/plan/design/` корня репозитория: папка вне git, и в worktree её нет. Окно Tauri, команды Rust и телефон проверяет человек.
5. Пул-реквест пушишь и открываешь сам. В описании, кроме `Closes`: решения, принятые без человека, скриншоты и список того, что проверить человеку в окне и на телефоне.
6. Сливаешь сам, при зелёном CI. Ревью идёт после слияния, правки по нему приходят своими задачами и пул-реквестами.

Решения, которые меняют формат сохранённых данных, маршруты api или формат команд Rust, добавляют зависимость или выходят за блок «Что нужно», принимаешь сам, но выносишь в пул-реквест отдельным пунктом.

Задачу откладываешь, а не ждёшь ответа, когда ей нужно что-то вне репозитория (аккаунт, токен, платный сервис, устройство) или три попытки починить одну и ту же проверку не помогли. В задачу пишешь комментарий, чего не хватает, и берёшь следующую. Ждёшь человека, только когда готовых задач не осталось.
