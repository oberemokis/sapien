# sapien

## Код

Устройство, слои и правила против связанности описаны в `docs/architecture.md`, направление зависимостей api и интерфейса проверяет `scripts/check-boundaries.mjs`. Новый модуль сначала получает место в дереве документа, потом код.

Команды: `pnpm typecheck` (tsc и `cargo check`), `pnpm lint` (oxlint, проверка границ, `cargo fmt --check`), `pnpm test` (vitest и `cargo test`). Все три гоняет CI, первые два ещё и хук перед коммитом. Api и окно приложения поднимает `pnpm dev`, api и интерфейс в браузере без Rust `pnpm dev:web`, api и Metro для телефона `pnpm dev:mobile`.

Expo ломает API от SDK к SDK, поэтому код телефона сверяется с документацией установленной версии: мажор `expo` из `apps/mobile/package.json` в `https://docs.expo.dev/versions/v<мажор>.0.0/`, оглавление в `https://docs.expo.dev/llms.txt`. Пакет в телефон ставится командой `pnpm expo install <пакет>` из `apps/mobile`: она подбирает версию под SDK.

pnpm ставит только версии старше суток (`minimumReleaseAge`). Если установка дописала `minimumReleaseAgeExclude` в `pnpm-workspace.yaml`, выбранная версия моложе: поставь предыдущую явно и удали запись.

## Коммиты

Формат первой строки здесь Conventional Commits по-русски: `<тип>(<область>): <результат>`. Это перекрывает формат первой строки из скилла `oberemokis-skills:commit`, всё остальное из него действует как есть: тело объясняет причину, автор только пользователь, хуки не обходятся.

- Тип: `feat` новая возможность, `fix` исправление, `refactor` перестройка без смены поведения, `perf` скорость, `test` только тесты, `docs` только документация, `chore` зависимости, CI, конфиги.
- Область: модуль, если правка живёт в одном, иначе сторона (`api`, `desktop`, `tauri` или `mobile`) или `ci`. Правка через весь репозиторий идёт без области: `docs: план функций`.
- Результат: одна фраза по-русски со строчной буквы, без точки, что стало, а не что сделано с файлами.
- Ломающее изменение маршрутов api, формата команд или сохранённых данных: `!` перед двоеточием и в теле строка `BREAKING CHANGE:` с тем, что сломается у потребителя.

Номер задачи в коммит не пишется: связь с задачей держит ветка и пул-реквест.

## Ветки

`main` единственная долгая ветка, пул-реквест в неё гоняет проверки (`.github/workflows/ci.yml`). Каждое изменение пишется в своей ветке и приходит в `main` пул-реквестом.

Ветка рождается из задачи на GitHub и носит имя `<тип>/<номер задачи>-<имя>`: тип тот же, что у коммитов (метка `feature` даёт `feat`, метка `bug` даёт `fix`), имя латиницей в kebab-case, два-четыре слова. У задач имя уже записано внизу строкой «Ветка для разработки:», его берёшь как есть.

Корень репозитория делят несколько сессий сразу. Ветка живёт в своём worktree рядом с репозиторием, корень остаётся на той ветке, где был: переключение в корне уносит чужую незакоммиченную работу и подменяет код под соседней сессией.

1. Задача. Номер называет человек, иначе `gh issue list --label feature`. Если задачи под изменение нет, предложи завести её с метками типа, `size: S|M|L` и `area: …` и дождись ответа: ветка появляется только после задачи.
2. Ветка и worktree одной командой: `git fetch origin`, затем `gh issue develop <номер> --name <ветка> --base main --checkout --worktree ../sapien-<номер>-<имя>`. Внутри `pnpm install`, дальше вся работа только там. Готово, когда `gh issue develop --list <номер>` показывает ветку, `git -C ../sapien-<номер>-<имя> branch --show-current` печатает её имя, а `git status` в корне такой же, как до шага.
3. Перед пул-реквестом `pnpm typecheck`, `pnpm lint` и `pnpm test` в worktree: это те же проверки, что в CI.
4. Пул-реквест. `gh pr create --base main --head <ветка>`, заголовок в формате первой строки коммита, в описании `Closes #<номер>`: слияние само закроет задачу.
5. После слияния. `git worktree remove ../sapien-<номер>-<имя>` и `git branch -d <ветка>`.

## Задачи
