# Архитектура

Два приложения в одной монорепе. `apps/api` это сервер на Hono под Node. `apps/desktop` это десктопное приложение для работы с агентом Claude Code на Tauri v2: процесс на Rust держит окно и доступ к системе, интерфейс на React рисует веб-вью в этом окне. Данные пользователя живут на его устройстве: проекты, сессии и действия окна читает и пишет Rust, а в api интерфейс ходит по HTTP через клиент Hono RPC только за тем, что без сервера не получить. Все стороны разложены вертикальными модулями: модуль это область данных со своей дверью, снаружи виден только вход в него, внутри слои. Имена слоёв общие, поэтому знание переносится между сторонами.

Основное правило именования: каталог задаёт слой, имя файла задаёт операцию. Роль в имени файла (`projects.router.ts`) не нужна, её несёт папка.

Правила ниже действуют до появления кода, который им подчиняется. Где кода ещё нет, правило описывает, каким он должен быть.

## Слои и направление зависимостей

Сервер:

```
transport → service → use-case → domain
infrastructure → domain
```

Интерфейс:

```
pages → components → flows → interactions → infrastructure
components → ui, model, store
```

Rust:

```
transport → use_case → domain
infrastructure → domain
```

Наружу не смотрит никто. `domain` и `model` не импортируют ничего своего. Сценарий не знает ни про Hono, ни про Tauri, ни про хранилище: он работает с портом. `core` не знает ни одного модуля, сборка приложения живёт в `app/`.

Проверяется скриптом `scripts/check-boundaries.mjs`, он входит в `pnpm lint` и в хук перед коммитом. Компилятор эти правила не ловит: TypeScript одинаково пропускает импорт вниз и наверх. Что проверяется:

- сосед берётся только через `index.ts` модуля, `core` не знает ни модулей, ни `app` (на сервере и через `#modules`, `#app`);
- сервер: домен знает только zod и свой `domain`; сценарий не знает адаптеров, транспорта и Hono; транспорт зовёт сценарии через `service`; адаптер не знает сценариев и транспорта; порты и сервис не знают адаптеров;
- desktop видит `@sapien/api` только импортом типа;
- интерфейс: `model` не импортирует значением react, TanStack, hono и Tauri (типы можно); `ui/` модуля не знает остальных его слоёв; `interactions` не знают экрана; клиент api, hono и Tauri живут только в `infrastructure` модулей и в `core`; `app`, `pages` и `components` не ходят в `infrastructure`.

На стороне Rust дверь держит сам язык: наружу модуля выходит только то, что объявлено `pub` в его `mod.rs`. Слой в Rust это файл (`domain.rs`), пока ему хватает одного, и каталог (`infrastructure/`), когда файлов несколько.

## Где живёт работа

Источник правды это устройство пользователя (local first). Приложение открывается, показывает и меняет данные без сети, а отсутствие сети не считается ошибкой.

Проект это папка на диске, в которой работает агент (модуль `projects`). Список проектов лежит файлом `projects.json` в папке данных приложения. Папку выбирает системный диалог в Rust, поэтому интерфейс не может подсунуть проектом чужой путь, а та же папка второй раз не добавляется. Убрать проект значит убрать его из списка вместе с сессиями, папку на диске приложение не трогает. Пропавшую папку окно показывает пометкой: сессии видны, а новый ответ и новая сессия отвечают `project_missing`. Сценарии агента получают путь проекта только через дверь `projects` (`projects::transport::folder`) и только если папка на месте.

Сессия это разговор с агентом в папке проекта (модуль `agent`). Каждая лежит файлом `sessions/<id>.json` в папке данных приложения: проект, название, время и id разговора Claude Code в поле `claude`. Сам разговор хранит Claude Code, sapien его не копирует. История чата из версий до формата 2 лежит нетронутой в `sessions/archive/`, окно её не показывает. Удаление сессии или проекта отказывает `agent_busy`, если в удаляемой сессии отвечает агент: ответ записал бы сессию обратно. Пока sapien сам Claude Code не запускает, и отвечающих сессий нет.

Окно показывает сессии вкладками (`agent/model/tabs.ts`). У каждого проекта свой набор вкладок, а видны вкладки открытого: сессия из левой панели открывается вкладкой своего проекта, «+» во вкладках начинает новую сессию в нём, а новый проект начинается с сессии сразу. Закрытая вкладка сессию не удаляет. Сессию, в которой отвечает агент, отмечает точка в левой панели и во вкладках.

Всё, что Rust пишет на диск, идёт через `durable.rs`: временный файл рядом, сброс на диск, переименование поверх и сброс папки. Оборванная запись или выключенное питание оставляют файл целым, в старой версии или в новой. Новый формат своего файла приложение пишет в новый файл тем же путём, а старый держит, пока перенос не закончился: оборванный перенос следующий запуск начинает заново со старого.

Синхронизации своей нет, учётной записи тоже: проекты и сессии живут на одном устройстве. Собственные файлы приложения не шифруются: их закрывает шифрование диска системы.

Блокировка приложения закрывает содержимое от чужого взгляда, пока человек отошёл, и включается в «Безопасности», по умолчанию она выключена. Окно закрывается после заданного времени без мыши и клавиатуры. Включённая блокировка закрывает приложение и с запуска. Заглушка на окне это модальный `<dialog>` поверх всех остальных, страница под ней остаётся смонтированной: действия по расписанию работают, несохранённое не теряется, а сочетания клавиш до неё не доходят. Снимает заглушку проверка системы: на окне команда `app_unlock` (`unlock.rs`, крейт `robius-authentication`) спрашивает Touch ID, Windows Hello или пароль учётной записи, на Linux пароль через polkit. Включить блокировку можно только после удачной проверки, поэтому без способа проверки она не включается вовсе. Если системе стало нечем спросить уже потом (сняли пароль учётной записи, нет агента polkit), заглушка снимается без проверки, иначе приложение закрылось бы насовсем: кто сидит в открытой сессии системы, и так читает файлы проектов с диска.

Формат собственных файлов приложения в папке данных имеет номер, файл `data-format` (`data_format.rs`). Новая версия при запуске, до окна, переносит файлы от записанного номера к своему по шагам и пишет номер после каждого шага, поэтому оборванный перенос следующий запуск продолжает с упавшего шага. Файла нет у новой установки и у версий до номера формата, это формат 1. Шаг держит прежний файл, пока новый не записан, как сказано выше, и не падает на пустой папке. Данные в хранилище окна (`localStorage`) переносит интерфейс сам, при чтении: каждый ключ и так читается с запасом на старое и испорченное.

Приложение обновляется из релизов GitHub (`updates.rs`, модуль `updates` окна). Версия живёт в одном месте, в `apps/desktop/package.json`: `tauri.conf.json` берёт её оттуда, у `Cargo.toml` версии нет. Тег `v<версия>` запускает `release.yml`: черновик релиза с заметками по пул-реквестам, сборки macOS (одна на Apple Silicon и Intel), Windows и Linux с файлами обновления, подписанными своим ключом, и публикация, когда `latest.json` собрал все системы. Окно проверяет `latest.json` последнего релиза при запуске и раз в шесть часов, без сети не проверяет вовсе. Найденную версию с тем, что в ней изменилось, предлагает карточка в углу окна, а ставится обновление только по «Обновить и перезапустить». Плагин updater качает его, сверяет подпись с открытым ключом из `tauri.conf.json` и версию внутри подписи с объявленной (`requireSignedVersion`): иначе подменённый `latest.json` поставил бы старую подписанную версию. Окно плагин напрямую не зовёт, у него только команды `app_update_check` и `app_update_install`, и ставится ровно то, что показала последняя проверка. Закрытый ключ подписи живёт в секретах окружения `release` на GitHub и у владельца, в репозитории только открытый.

Агент это Claude Code на устройстве со входом по подписке Claude, пока только на macOS. Rust ищет `claude` по абсолютным путям установки (`agent/infrastructure/claude_code.rs`), потому что приложение из Finder не видит PATH оболочки, и проверяет версию (не ниже 2.1.299) и вход (`claude auth status`). Окружение Claude Code собрано заново: без ключей API, иначе ключ перебил бы вход по подписке, с PATH из путей установки, `SHELL` и `SSH_AUTH_SOCK`, чтобы команды и git работали как в терминале, а необязательный трафик и автообновление выключены переменными. Строки Claude Code в журнал не идут. Посередине окна сессия пока показывает только то, что мешает агенту работать: Claude Code не готов или папки проекта нет.

Лимиты подписки за пять часов и за неделю отдаёт команда `agent_usage`. Rust запускает `claude -p --input-format stream-json` в папке данных и шлёт управляющие запросы, как Agent SDK: первым `initialize`, за ним `get_usage` с `skip_behaviors`, как `/usage` в терминале. Сообщения не уходит, поэтому подписка не тратится. Лимиты у claude.ai спрашивает сам Claude Code своим входом, поэтому токен sapien не видит. Из ответов берутся только проценты и время сброса окон, а данные аккаунта, расход сессии и разбор по скилам не берутся. Окно спрашивает лимиты, только пока открыта карточка «Claude» в нижней полосе, и раз в минуту, пока она открыта: каждый запрос запускает Claude Code.

С машины файлы проектов уходят только через Claude Code и только в Anthropic, по правилам, которые человек задал Claude Code. Свои запросы Rust шлёт только на свой адрес (`egress.rs`): GitHub на адрес из кода, GitLab на тот, что ввёл человек. Обновление ходит своим клиентом плагина на GitHub по адресу из `tauri.conf.json`, без ключей и без данных человека. Перенаправлениям клиенты не следуют, потому что с ними токен ушёл бы на чужой адрес, а отказ пишется в журнал приложения одним источником адреса, без пути и параметров.

Действие это сохранённое задание агенту, файл `.md` в папке `actions` данных приложения, общий для всех проектов (модуль `actions`): имя файла это название, текст под шапкой это задание, в шапке `hotkey` и `schedule`. Rust хранит файлы и проверяет имя, а разбирает их окно (`agent/model/actions.ts`). Экран «Действия» заводит, правит и удаляет их, а запускать их sapien пока не умеет.

Расписание это `schedule` вроде `пн, чт 9:30` или `Mon 10:00` по часам устройства. `{{since}}` и `{{today}}` в задании это прошлый запуск, первый раз неделя назад, и сегодня.

GitHub и GitLab подключаются по личному токену (модуль `forge`). Токен уходит в Rust и лежит в системном хранилище паролей, адрес сервера и логин лежат файлом `forge.json` в папке данных. Подключение сохраняется, только когда сервер ответил владельцем токена (`/user` у GitHub, `/api/v4/user` у GitLab), а ответ не от API даёт `forge_host_invalid`. GitLab бывает своим, его адрес только по https. Что агент делает с подключёнными сервисами и что попадает во «Входящие», пока не решено: экран «Входящие» это заглушка.

Api держит только то, что без сервера не получить: внешние источники, которым нужен сервер, и синхронизацию, если она появится. Проекты и сессии через api не ходят. Rust держит то, что принадлежит машине: файлы, окна, системные API. Интерфейс показывает и не решает того, что может проверить Rust или сервер.

Настройки устройства (тема, ширина панели, модель, открытые вкладки, время запусков действий) интерфейс хранит в `localStorage` окна: они принадлежат устройству и между устройствами не переезжают.

## Правила

### Модуль выставляет наружу один файл

`modules/<m>/index.ts` отдаёт на сервере фабрику модуля, на интерфейсе именованные хуки и компоненты. `modules/<m>/mod.rs` отдаёт команды и то, что нужно корню для сборки. Внутренности модуля снаружи не импортирует никто.

Исключение одно: тест подменяет границу процесса и потому знает, какой файл её держит.

### Путь наружу модуля идёт через псевдоним

В desktop `@/` указывает на `src`. В api псевдонимы объявлены в `imports` его `package.json`: `#core/*`, `#app/*` и `#modules/*`, причём последний ведёт прямо в `index.ts` модуля, так что внутренности соседа по нему не достать вовсе. Внутри модуля импорт относительный (`./ports`, `../domain/x`), за его пределы только по псевдониму. Внутри `core` то же правило: соседний каталог берётся через псевдоним, файл рядом как `./client`.

Так путь перестаёт зависеть от глубины файла: `../../../../core/config/env` читается как загадка и ломается при первом же переносе. Относительный путь внутри модуля оставлен намеренно, иначе переименование модуля правило бы каждый файл внутри него.

Псевдоним desktop объявляется всем, кто резолвит импорты сам: `tsconfig.json` для компилятора, `vitest.config.ts` для тестов, `vite.config.ts` для сборки. Пропущенный резолвер падает не на сборке, а на первом запуске. Псевдонимы api из `imports` Node, TypeScript, tsx и tsup понимают без настройки. Через `paths` в tsconfig их завести нельзя: desktop проверяет исходники api своим компилятором, и там `@/` ведёт в другое место.

Обойти границу через псевдоним нельзя: `scripts/check-boundaries.mjs` сводит `@/modules/projects/model/x` и `../../projects/model/x` к одному и тому же адресу.

### Тип приложения уходит на клиент отдельным файлом

`apps/api/src/app/app.type.ts` содержит только `export type AppType`, и `exports` пакета отдаёт только его. Desktop берёт тип импортом `import type { AppType } from "@sapien/api"`, значимый импорт запрещён проверкой границ: он утащил бы сервер в бандл приложения.

### Маршруты идут одной цепочкой

Клиент Hono RPC выводит тип из цепочки вызовов, поэтому маршрут объявляется как `new Hono().get(...).post(...)`, а модуль встаёт в приложение через `.route("/projects", projects)` в той же цепочке. Маршрут, добавленный отдельной строкой `app.get(...)`, клиенту не виден.

Обработчик возвращает ответ через `async`/`await`: цепочка `.then()` теряет тип, и клиент видит `unknown`. Статус пишется явно, `c.json(data, 200)`: так он попадает в тип ответа, и клиент сужает тип по `res.status`. «Не найдено» отдаётся через `c.json(..., 404)`, а не `c.notFound()`, у которого типа нет.

Вход проверяет валидатор на маршруте (`zValidator` из `@hono/zod-validator` со схемой zod), и тип входа клиент берёт из него. Параметры пути и запроса на клиенте всегда строки, даже если схема их приводит.

Версия hono у api и desktop одна, её держит `catalog` в `pnpm-workspace.yaml`: при двух версиях типы клиента ломаются до «excessively deep». Strict включён в `tsconfig.base.json` для обеих сторон, без него типы RPC в монорепе не выводятся.

Когда маршрутов станет столько, что подсказки в редакторе начнут тормозить, тип клиента предвычисляется: api отдаёт `hcWithType`, обёртку над `hc` с готовым типом, а desktop зовёт её вместо `hc`.

### Ошибка это код, а не текст

Ошибка несёт вид (для статуса) и код. Сервер переводит вид в статус в одном месте и кладёт код в тело ответа, текст не отдаёт вовсе. Ответы из `app.onError` клиент Hono не выводит, поэтому ошибка, которую экран должен разобрать, возвращается из маршрута через `c.json({ code }, status)` или попадает в тип через `ApplyGlobalResponse`. Команда Rust поступает так же: `Result<T, AppError>`, где `AppError` сериализуется в вид и код. Перевод делает интерфейс по коду.

Исключение одно: объяснение отказа от чужого сервера, например ответ GitLab на запрос, который он не принял. Команда кладёт его рядом с кодом в `detail` как есть. Перевести его нельзя, а без него причину отказа не найти, поэтому интерфейс показывает его после своего текста по коду.

### Окно ходит в api по адресу, а не через прокси

Окно Tauri грузится со своего origin (`tauri://localhost` на macOS и Linux, `http://tauri.localhost` на Windows), поэтому прокси дев-сервера ему не поможет: клиент в `core/api/client.ts` ходит по абсолютному адресу из `VITE_API_URL`, по умолчанию `http://localhost:3400`. Api пускает эти origin через CORS в `app/app.ts`, дев-сервер Vite на 1420 только вне продакшена.

Адрес api стоит в трёх местах, и разъехаться им нельзя: `PORT` сервера, `VITE_API_URL` окна и `connect-src` в CSP окна (`src-tauri/tauri.conf.json`). Новый адрес, например боевой, добавляется во все три.

### Порт объявляет потребитель

На сервере `modules/<m>/ports.ts` описывает, что нужно сценариям, а `infrastructure/` это выполняет через `satisfies`. Реализацию к типу объявлять не надо: структурная типизация делает порт бесплатным. В Rust порт это trait в `ports.rs`, и реализация объявляет его явно, поэтому trait заводится только на границе с внешним миром.

Явный порт нужен только на границе, смотрящей во внешний мир. Внутрь типы текут сами: транспорт берёт сервис как `ReturnType` фабрики.

### Сценарий это фабрика на портах

На сервере `makeRenameProject(ports)` возвращает функцию, которая принимает вызывающего и вход. Приставка `make` означает сценарий, `create` означает адаптер, сервис или модуль. `service.ts` это список готовых сценариев, а не десяток стрелок, перекладывающих аргументы. Сценарий делает одно дело: «прочитать запись» и «завести её при первом обращении» это один сценарий, а не два.

Команда Rust и маршрут Hono только разбирают вход, зовут сценарий и ничего не решают сами.

### Интерфейс знает про сеть и Rust в одном слое

`infrastructure/<модуль>.api.ts` это единственное место модуля, где живут клиент api, `invoke`, события и плагины Tauri. Выше по слоям ходят за данными модуля, а не за маршрутом или командой.

`interactions/` держит кеш: ключ, `staleTime`, `enabled`, инвалидация. Центрального реестра ключей нет, ключ выводится из пути маршрута или имени команды. Мутация идёт через `useMutation` из TanStack Query и после успеха инвалидирует кеш по префиксу ключа.

Данные сервера живут только в кеше Query и в стор не копируются: копия расходится с кешем при первой же инвалидации. `store/` держит то, чего на сервере нет и что нужно нескольким компонентам (вкладки, идущие ответы). Состояние одного компонента остаётся в `useState`.

`flows/` появляется там, где экран собирает больше одного источника. Где источник один, потока нет: пустая обёртка вокруг запроса ничего не объясняет.

Окно без процесса Rust (`pnpm dev:web`, тесты) команд не получит: `invoke` там падает. Тест подменяет границу через `mockIPC` из `@tauri-apps/api/mocks`, а сеть через подмену `fetch`, но не свой `infrastructure`.

### Права окна объявляются явно

Плагин Tauri получает права в `src-tauri/capabilities/default.json`, иначе его вызов падает отказом во время работы, а не на сборке. Право выдаётся на окно и на конкретное действие плагина, а не набором `*:default`, если набор открывает больше, чем нужно экрану.

CSP задан в `tauri.conf.json` и в разработке выключен (`devCsp: null`), потому что Vite вставляет стили и держит сокет горячей замены. Новый источник (адрес api, шрифт, картинка из сети) расширяет CSP точечно по директиве.

### Окно показывает только свой интерфейс

Ответ агента собран из чужого текста: файлов проекта, вывода команд, страниц из сети. Он поэтому считается чужим, а у окна есть доступ к системе через команды Rust. Отсюда правила.

- Окно строит `links.rs`, а не конфиг (`"create": false`): только так на него вешаются проверки переходов. Переход на чужой адрес отменяется, новые окна запрещены, адрес `http`, `https` или `mailto` уходит в браузер системы. Другие схемы не открываются нигде.
- Окно показывает ответ агента текстом, HTML из него не выводится. `dangerouslySetInnerHTML` запрещён правилом oxlint `react/no-danger`. Разметка ответа, когда появится, сначала его очистит.
- Ссылка открывается через команду `open_link`: адрес проверяет Rust, окно его только передаёт.
- Права окна в `capabilities/default.json` перечислены поштучно, без `core:default`. Новой возможности окна нужно своё право с причиной в описании.
- CSP закрывает `object-src`, `frame-src`, `form-action` и держит `base-uri` на своём origin. Разрешение на скрипт со стороны в него не добавляется.

### Секрет живёт в системном хранилище и в Rust

Токены GitHub и GitLab лежат в системном хранилище паролей: Связка ключей на macOS, диспетчер учётных данных на Windows, Secret Service на Linux. На окне с ним работает `secrets.rs` через крейт `keyring`.

- Окно отдаёт токен в Rust один раз, командой `forge_connect`, и сразу забывает: поле пустеет сразу после отправки. Обратно приходят только адрес сервера и логин. Команды, которая вернула бы токен, нет и не будет.
- Запрос с токеном делает Rust и подставляет его сам через `Secrets::get`, заголовок помечен как чувствительный. Токен не попадает в файлы настроек, историю сессий, журнал, логи, тексты ошибок и экспорт. Агенту он не передаётся.
- Имя секрета это вариант `SecretName`: окно не может записать в системное хранилище ничего, кроме известных записей. Новый секрет добавляет свой вариант.
- Где системного хранилища нет (Linux без Secret Service), токен живёт только в памяти Rust до закрытия приложения, после перезапуска подключение показывается отключённым. Своего шифрования и открытого текста на диске нет.

### Состояние «в пути» отличается от «нет»

Пока данные `undefined`, экран показывает заглушку того же размера, а не пустой список. Ожидание не меняет размеры элемента: подпись кнопки остаётся, меняется значок той же величины.

### Соседние модули связывает страница

Модуль не импортирует соседа значением, даже через дверь, если связь нужна только на одном экране: её собирает страница. Карточка одного модуля даёт слот, страница ставит в него компонент другого.

### Ключ перевода проверяет компилятор

`core/i18n` запускает i18next и объявляет основной словарь в `CustomTypeOptions`. После этого `t` из `useTranslation()` принимает только существующие ключи в любом файле, и опечатку ловит компилятор. Словарь без этого объявления превращает `t` в функцию от любой строки.

### Переход идёт по пути из дерева

`Link` и `navigate` берут `to` и `params` из дерева маршрутов (`src/route-tree.gen.ts`), и оба проверяет компилятор: переименованная страница ломает сборку, а не ссылку. Путь, собранный строкой (`` `/projects/${id}` ``), компилятор не проверит, поэтому параметр передаётся через `params`. Параметры запроса страница описывает в `validateSearch` схемой zod и читает через `useSearch`, а не из `window.location`.

Дерево пишет плагин роутера при `vite dev` и `vite build`, и оно лежит в репозитории: `tsc` в CI запускается без Vite.

### Готовое вместо самописного

Промежуточные слои сервера берутся из `hono/*` (`hono/cors`, `hono/logger`), загрузка и кеш из TanStack Query, адрес из TanStack Router. Подписка на событие браузера идёт через `useSyncExternalStore` или эффект с отпиской в cleanup: своя версия без отписки рано или поздно течёт. То же для Rust: системное API берётся плагином Tauri, если плагин есть.

### Пакет появляется при втором потребителе

Пакет это граница, а не папка. Типы между api и приложениями едут через `AppType`, поэтому пакета контрактов нет. Пакет в `packages/` появляется, когда один и тот же код нужен двум приложениям значением: схема zod, коды ошибок.

### Тест лежит рядом с проверяемым

Тест это `*.spec.ts` (`*.spec.tsx`, если в нём разметка) рядом с файлом. На сервере основная масса входит через приложение или дверь модуля клиентом `testClient` из `hono/testing`: настоящая цепочка маршрутов, подмена только на границе процесса и на портах чужих модулей. Модуль в тесте собирается через дверь, а не из внутренностей: тогда перекладка файлов внутри модуля тесты не ломает. Изолированные тесты только у домена и у чистой модели интерфейса. Тест Rust живёт в `#[cfg(test)] mod tests` того же файла; сценарий проверяется на двойниках портов, команда через `tauri::test`.

## Как добавить

Маршрут в существующий модуль api: файл в `use-case/`, строка в `service.ts`, маршрут в цепочке `transport/`, при новом хранилище файл в `infrastructure/`. На интерфейсе метод в `infrastructure/<модуль>.api.ts`, файл в `interactions/` и строка в двери модуля.

Команду Rust: сценарий в `use_case`, функция с `#[tauri::command]` в `transport`, строка в `generate_handler!` в `lib.rs` полным путём `модуль::transport::команда`. Макрос ищет рядом с командой скрытые функции, которые переэкспорт через `pub use` не уносит, поэтому `transport` открыт из `mod.rs` целиком. На интерфейсе так же, как для маршрута.

Модуль: каталог по шаблону выше на нужной стороне, `.route()` в `app/app.ts` api или `mod` в `lib.rs`, каталог в `src/modules/` интерфейса, страница в `pages/` окна.

Если шагов выходит больше, значит общее не доехало до `core/`.

## Отвергнутые варианты

Слои сверху, модули внутри (`layers/use-case/<сущность>`). Барель на каждом слое открывает любой сценарий любому файлу, а сущность размазывается по четырём каталогам. При модулях сверху дверь одна и её стережёт проверка границ.

Клиентский `use-case` на каждый маршрут и команду. Половина сценариев была бы строкой «вызови api». Слой заведём, когда у сценария на интерфейсе появится что решать; пока эту роль несёт `interactions`.

tRPC поверх Hono. Второй протокол внутри HTTP со своим роутером и своим клиентом, тогда как Hono RPC выводит тип клиента из тех же маршрутов, а ответ остаётся обычным HTTP, который читает любой клиент.

Vue вместо React. React выбран в расчёте на приложение для телефона: Expo работает только на React Native, а у Vue аналога нет (Vue Native заброшен, NativeScript-Vue сильно меньше, остальные варианты это webview). Телефон отложен, но если он вернётся, его интерфейс напишется на том же языке, что и окно.

TanStack Start вместо голого React. Tauri раздаёт окну статические файлы, серверного рендеринга там нет. Сервер у нас Hono, и серверные функции Start его бы продублировали.
